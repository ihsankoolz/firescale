# 0064 — The command the stop hook starts, and what the hook files affect

Status: accepted (2026-11-16, for 0.5.2). Changes ADR 0014 on one point: the default of `hooks install --bin` was `fscale`. Narrows ADR 0036 (every file that belongs to no project is in every step's key) and ADR 0032 (such a file affects every project) for three files, the way ADR 0058 did for `firescale.config.json`. ADR 0027's `agent-ready/verify-hook` fix is unchanged; `hooks install` now uses its command.

## Context

Two findings of the 0.5.1 run on the course project (`docs/reviews/cs464-0.5.1.md`):

- **Finding 6.** In a clone of the course project (no root `package.json`, `fscale` not on the PATH), `npx firescale@0.5.1 hooks install --all` wrote `fscale hooks run --agent <name>` into the three hook files and said "Each agent now runs ...". Run by hand, `cmd /d /s /c "fscale hooks run --agent claude"` gave `'fscale' is not recognized as an internal or external command, operable program or batch file.` and exit 1. A stop hook that exits 1 lets the agent stop: verify never ran, and nothing said so.
- **Finding 5.** In the same copy, after `hooks install --all`, `verify --affected --json` gave `"reason": ".claude/settings.json belongs to no project"` for all six projects. The files firescale had just written ran every project, a 1 h 40 min run on that repo, until they were committed. The same finding reports an untracked `verify.log` at the root doing the same.

The owner asked for five things: a command that starts where `fscale` is not on the PATH, on Windows too; a check at install that says plainly when it cannot start; a stop hook that cannot start must never look like a pass, with what each agent does written down from its own docs; a decision on whether the hook files can change a step's result; and no change for `*.log`, only an entry under "Needs your decision".

Two more facts from Claude Code's page: a `Stop` hook that exits 2 with nothing on stdout and a stderr that says a file is missing ("No such file or directory") is a non-blocking error, and exit 1 "without valid JSON output is a non-blocking error". From npm's docs (<https://docs.npmjs.com/cli/v10/commands/npm-exec>): "When standard input is not a TTY or a CI environment is detected, `--yes` is assumed", so `npx` in a hook never waits at its install prompt.

So in all three agents a stop hook that cannot start lets the agent stop, as fscale's own exit 1 does on purpose.

## Decision

### 1. Without `--bin`, the repo decides the command

`hooks install` writes the command `fscale_command` gives, the one the `agent-ready/verify-hook` fix and the AGENTS.md block already use (ADR 0027):

- the root `package.json` has an `fscale` script: `pnpm --silent fscale`, `yarn --silent fscale`, `bun run --silent fscale`, or `npm run --silent fscale --`, by the repo's package manager;
- otherwise `npx firescale`.

A command given with `--bin` is written as it is, unchanged.

The function moved from `crates/rules/src/agent-ready/managed.rs` to `firescale_core::hooks`, so the CLI and the rules share it; managed.rs re-exports it.

Why:

- **Not this machine's PATH.** The hook files are committed; the person who runs `hooks install` is one of several machines that will start the command. A default that depends on what is on the installer's PATH (`fscale` when it is found, `npx firescale` otherwise) would write a command that works for them and not for a teammate, which is finding 6 the other way round.
- **`npx firescale` starts wherever Node.js is installed,** on Windows too (`npx.cmd`, and the `npx` script Git Bash finds). It runs the firescale in the repo's `node_modules` when there is one, so a repo that installs firescale gets its own version without a download.
- **Not pinned.** The CI workflow's tamper guard runs `npx --yes firescale@<version>` because the base branch must choose the program a `pull_request_target` job runs (ADR 0045). The CI `verify` job, the AGENTS.md block and the verify-hook fix all run unpinned `npx firescale`. A pinned hook would hold one version for every teammate, which is good, but it would differ from the `fscale verify` an agent is told to run in AGENTS.md, and `hooks install` would not update it on an upgrade (a hook counts as installed whatever its prefix, ADR 0014). `--yes` is not needed: npm assumes it when stdin is not a terminal, and an agent pipes JSON into the hook. Listed under "Needs your decision".
- **What npx costs.** Measured on the owner's Windows machine while other builds ran: `npx --yes firescale@0.5.1 --version` and `npx --yes firescale --version` each took 7 to 10 s per start once firescale was in npm's cache, about the same for both. Both started with `--offline` once cached; an uncached version with `--offline` stopped with `ENOTCACHED`. The first start on a machine downloads firescale (one package and its native binary). A real loss of network was not tried: unverified. Inside a stop hook that runs verify, the start is a small part; a repo that wants it faster adds an `fscale` script or passes `--bin`.

### 2. `hooks install` starts the command and says what happened

After the files are written, `hooks install` takes the command of each hook file that holds the hook (the text before `hooks run --agent <name>`, written now or already there; a refused file is skipped), and starts each distinct one as `<command> --version`:

- the way an agent does: in the repo root, through `cmd /D /S /C` on Windows and `sh -c` elsewhere (the same shell doctor uses), with stdin closed, with a time limit of 120 s;
- having said first, on stderr, what it runs: ``fscale: checking that the hook can start: running `npx firescale --version` in the repo root, as an agent would.``, and then `npx may download firescale from the npm registry first.` for an npx command, or ``It runs this repo's own `fscale` package script.`` for a package manager's script;
- an answer whose last line is a version: ``The hook starts on this machine: `npx firescale --version` answered 0.5.2.`` When it is not this fscale's version, the line adds `That is not this fscale (0.5.2): the agent will run firescale 0.4.0.` That is a note, not a failure;
- anything else (a non-zero exit with the last 10 lines it printed, an answer that is not a version, no answer within 120 s, a shell that does not start): `The hook cannot start on this machine: ...`, then one paragraph that says the agent would stop without verify having run, what to do, and that the files are written; the exit code is 1. A refused file still gives 2.

The files are kept when the check fails: the command may start on a teammate's machine (a package script before `pnpm install`, say). Since a hook counts as installed whatever its prefix, the paragraph says to edit the command in the files or remove the hook before running again with `--bin`.

Why start it rather than look for the program on the PATH: `npx` on the PATH does not mean firescale resolves (finding 9 of the review: npx itself printed `'fscale' is not recognized` 7 times), `npx fscale` is another package, and a package script needs the repo's dependencies. Starting it answers all three.

Why allow the download rather than `npx --no`: the agent's first stop would download it anyway, inside a hook with a time limit. Doing it at install moves the wait, and any failure, to a moment the person is watching, and the stderr line says it before it happens. A package script is the repo's own code; the hook runs it at every stop, and the stderr line says so here too.

The check is close to the agent's start, not the same: Claude Code runs Git Bash or PowerShell on Windows, Codex the session's shell, Cursor PowerShell; and an agent started from a desktop app may have another PATH than the terminal. `docs/hooks.md` says so.

Tests stand in for `npx`, `pnpm` and a `--bin` command on a PATH the test builds (`hooks.test.ts`, "the command the hook starts"): the folders of this machine's PATH that hold an `npx` or an `fscale` are left out, and on Unix a folder with a link to `/bin/sh` comes first. No test downloads anything. Every other `hooks install` test now runs with a stand-in `npx` first on the PATH for the same reason.

### 3. A stop hook that cannot start: caught at install, not wrapped

The owner's example was a command written so that a failed start blocks with a message, while fscale's own exit 1 keeps its meaning. That was considered and not done:

- **One file serves every OS and shell.** The same committed `.claude/settings.json` runs under `sh` on a Mac, Git Bash or PowerShell on Windows; Codex's runs under the user's shell or `cmd`; Cursor's under PowerShell on Windows. "Run it, and exit 2 with a message if it did not start" has no syntax common to `cmd`, Windows PowerShell 5.1 and `sh`: `||` is not valid in Windows PowerShell 5.1, `1>&2` is not valid in PowerShell, and `;` does not separate commands in `cmd`. Codex's `commandWindows` and Claude Code's `shell` field narrow it, but a Codex session's shell on Windows is the user's (unverified which), and Claude Code has no command per OS that we found.
- **A launcher's failure and fscale's release share exit 1.** npx exits 1 for its own errors (`could not determine executable to run`, `ENOTCACHED`), the code fscale uses on purpose to let the agent go (ADR 0014). A wrapper would have to read their output to tell them apart.
- **A wrapper's block has no loop guard.** The count of blocks in a row lives in fscale, which did not start. The agent would be sent back with a message it cannot act on ("Claude can't repair a hook that won't run", in Claude Code's words), up to the agent's own cap: none found for Codex. ADR 0014 holds that a broken tool must not trap an agent.
- **The agents chose this.** Claude Code refuses `onFailure: "block"` on stop hooks, and treats a stop hook's exit 2 that reads like a missing file as non-blocking.

What is done instead: the default command starts on more machines (1), `hooks install` proves the command starts and says plainly when it does not (2), and `docs/hooks.md` lists what each agent shows when a stop hook fails. fscale's own exit codes are unchanged. Listed under "Needs your decision", with the option that remains: `fscale doctor` could start the hook command too, so that a machine where it stopped working is found by the command agents are told to run.

**Decision.** Like `firescale.config.json` as a file (ADR 0058), the three files at the repo root, and only those three paths, are files only of the units whose scope holds the repo root (`Scope::holds_root`: the repo root's own steps, a project at the root, a folder only named in `verify.projects` or one the graph cannot place, and a project that uses one of those). For every other unit:

- **The step cache** (`stepcache::covers`): the files are not in its key. So `same_on_base` of blame-aware verify, the base store's key and the shared CI cache follow, since all three use `covers`.
- **`verify --affected` and the stop hook** (`verify_plan` in `crates/cli/src/main.rs`): the files go to `graph::affected_except` as settled files, the list the config already used: a changed file of the root project only, never "belongs to no project". `configkey::mark_file_readers` then runs every other unit whose scope holds the root, with the reason `.claude/settings.json and 2 more changed, and these steps can read every file of the repo, the agent hook files among them`. When no such unit is in the plan, a note says so: `3 changed files (.claude/settings.json and 2 more) are agent hook files, which only a step that can read every file of the repo could read, and no such step runs here, so they run nothing; the check still covers them.`

Not on the list, and still in every key and affecting every project like any file no project owns: any other file under `.claude/`, `.codex/` or `.cursor/` (`settings.local.json`, `.claude/hooks/*.sh`, the skills `agent-skills` writes, `.codex/config.toml`, `.cursor/cli.json`), and these three names inside a project's folder, which are that project's. A script a hook runs is code; the others were not part of the report. Listed under "Found while fixing, not fixed".

The cache format stays 2. A key made now for a unit below the root lacks the three files; a kept pass from 0.5.1 made without them (no hook files then) has the same key and is still true, and one made with them simply misses once.

### 5. A stray `.log` file at the root: no change

An untracked `verify.log` at the course project's root ran all six projects (finding 5), as documented: a file no project owns runs everything. `*.log` is not added to the "runs nothing" list. A log can be read by a test (a fixture, a parser's sample) or written by a step and then read by the next, so it can change a result; a stray one costs a full run. The trade-off is listed under "Needs your decision"; nothing was changed for it.

## Consequences

- In a repo with no root `package.json`, `hooks install` writes `npx firescale hooks run --agent <name>` where it wrote `fscale hooks run --agent <name>`. A repo with an `fscale` script gets that script. A person who relied on the old default passes `--bin fscale`.
- `hooks install` starts a program: npx (which may download firescale), a package script of the repo, or the `--bin` command. It says so on stderr first, and exits 1 when the command does not start.
- An agent whose stop hook cannot start still stops without verify having run; the install check and `docs/hooks.md` make that visible, the agents do not.
- After `hooks install` on a repo with no root project, `verify --affected` and the stop hook run nothing for the three files, and a full verify takes every project's pass from the cache. The repo root's own steps and a root project run, as they read every file.
- **Snapshots changed on purpose** (`hooks.test.ts.snap`): the written command is `npx firescale hooks run --agent <name>` in a fixture with no `package.json`, and stdout ends with the line of the check. The help snapshot (`cli.test.ts.snap`) has the new default of `--bin`.
- **Known limits.** The check uses `cmd` or `sh`, not the agent's own shell. A hook command that starts only inside an agent's environment (a variable it sets) is reported as not starting. A test of a project below the root that reads a hook file by its path is not run again when the file changes.
