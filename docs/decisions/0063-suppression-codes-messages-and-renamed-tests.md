# 0063 — Suppression codes, failure messages and renamed tests in the tamper guard

Status: accepted (2026-11-16; revised the same day after a fresh review of the first version, and on 2026-11-17 after the review of pull request 66). Refines ADR 0044 (suppressions, keyed `tool:rule`), ADR 0046 (`expected-changed`) and ADR 0042 (net counts over the whole change).

## Context

The 0.5.1 review ran the tamper guard on 150 commits of the course project (`docs/reviews/cs464-0.5.1.md`, "Tamper guard on 150 commits of main"). It gave 61 findings: 58 `suppression-added` and 3 `expected-changed`. 15 of the 58 and all 3 of the 3 were false.

- **Finding 3.** `# noqa: E402  (after the backend is chosen)` gave six findings: `noqa:E402`, then `noqa:(after`, `noqa:the`, `noqa:backend`, `noqa:is` and `noqa:chosen)`. `codes()` in `suppress.rs` split the text after `noqa:` at commas and white space and kept every word. The same split served `pylint: disable=` and `# nosec`.
- **Finding 4, two of three.** `expected-changed` compared an assertion's whole text with its literals masked. A changed failure message is a changed literal, so `pytest.fail("… the publish …")` → `pytest.fail("… a publish …")` and `assert idle == 0, f"… the gate's call"` → `assert idle == 0, f"… the refresh"` were taken for changed expected values.
- **Finding 4, the third.** A test was renamed and lost `assert upstream.calls == 1`; a new, different test of the same file had `assert upstream.calls == 0`. Every gone test was taken for a possible rename of every new test (M26), so the two were paired as one changed value. The real change, an assertion dropped from the renamed test, was not reported: the new test's assertions made up the count (ADR 0042).

A fresh review of the first version of this pull request found that some of its fixes lost changes the guard had caught before: a test moved to another file was taken for a rename of a test left behind, a value changed in two tests merged into one (or one split in two) was not reported, pylint and bandit codes after a word of prose were dropped, several message tables took a value for a message, a fail call outside an `if` lost its value, and one renamed test's loss was named twice. Two more were found after those fixes: JUnit 4's `Assert.assertEquals` after `import org.junit.*;`, and node's legacy four-argument `assert.fail`. Each got a failing test first, then a fix; the rule in section 0 decided each one. The review of pull request 66 found five more: kotlin.test's expected value taken for a JUnit 4 message, a pylint id in lower case and a `noqa:` list with no ruff-shaped first word no longer read as codes, an honest split named as a loss, and a literal that is no expected value in the `if` around a fail call.

## Decision

Each item first got a failing test, then the smallest fix that made it pass. The review's three cases were built from its exact output and went into `bench/tamper-corpus.json`; the cases the fresh review found are Rust unit tests in `crates/core/src/tamper/mod.rs` and `suppress.rs`. The held-out `bench/tamper-cheats.json` was only run for its numbers; its cases were not read.

### 0. When unsure, a value (owner's decision)

When the guard cannot tell whether an argument is a message or a value, or whether a word is a code or a comment, it keeps it as a value or a code. A false finding is acceptable; a new miss is not. Each change below is held to that. Where a message is left out, a value written as a string in the message's place can still be missed; those cases are listed under "Not done".

### 1. A code list ends where the tool's own reading ends

After `noqa:` the words are read in order, split at commas and white space, and the list ends at the first word that is not a code. Words after it, such as a trailing comment, are never codes. This is what Ruff and flake8 do.

**pylint and bandit are the exception (owner's decision, accepted).** Both tools read on past a word that is not a code: pylint reads every word of `disable=` up to a `;`, and bandit matches every word of its list. Stopping at the first word that is not a code would hide a code after it (`disable=unused-import unused-variable`, `# nosec B602 and B607`). So after `pylint: disable=` (and `disable-next=`) and after `nosec`, every word shaped like a code of that tool is kept, wherever it is in the list; a word that is not shaped like one is left out. A word of prose is not a code, so the review's comment words are still left out.

The shape of a code, by tool:

| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |

### 2. A failure message is not an expected value

Each assertion now carries what it checks without its failure message (`Assertion::checked`). `expected-changed` pairs on that, and an assertion whose only change is in its message is unchanged. Which arguments are the message comes from each framework's documented signature, by the name of the call:

- **Python:** the message after `,` of an `assert`; unittest's `msg` (after 1 value for `assertTrue`, `assertFalse`, `assertIsNone`, `assertIsNotNone`; after 2 for `assertEqual`, `assertIn`, `assertAlmostEqual` and the rest of the two-value asserts); numpy.testing's `err_msg` (after 2). `msg=` and `err_msg=` by name too.
- **JS and TS:** `expect(value, message)` (Vitest, Jest with a message, Playwright); node's `assert(value, message)`, `assert.ok`, `assert.equal` and its family (after 2); chai's `assert.isTrue` and the like (after 1) and `assert.equal`, `include`, `lengthOf`, `match` (after 2). `assert.fail` is all message only with one argument: node's legacy `assert.fail(actual, expected, message, operator)` keeps every argument as a value.
- **Rust:** the format and its arguments after 1 value (`assert!`, `debug_assert!`, `prop_assert!`) or 2 (`…_eq!`, `…_ne!`, `…_matches!`), when the argument there starts as a string. The commas inside a turbofish or a qualified path (`row.get::<_, String>(0)`, `<T as F>::f()`) do not split the arguments.
- **Go:** testify's `msgAndArgs` after the values each assertion takes (1 for `True`, `Nil`, `NoError` and the like, 2 for `Equal`, `Contains`, `Len`, `ErrorIs` and the like, 3 for `InDelta`, `InEpsilon`, `WithinDuration`, `Eventually`), the same for its `…f` forms, after `t` for the package functions; gomega's description after the matcher. testify's table is used for package functions only when the package is imported from `github.com/stretchr/testify/`: gotest.tools' `assert.Error(t, err, "boom")` checks its last argument, so it keeps every argument. testify's object form (`assert.New(t)`) and suites use the table as before.
- **Java:** JUnit 5 and TestNG's trailing `message` (after 1 or 2 values); AssertJ's `as`, `describedAs`, `withFailMessage`, `overridingErrorMessage`; the message after `:` of an `assert`. In a file that imports JUnit 4's `Assert` (`org.junit.Assert` by name or statically, or `import org.junit.*`), the message is the first argument, when the call has one argument more than the values it checks and that argument is written as a string (`assertEquals("name", expected, actual)`); a call on `Assertions.` still takes JUnit 5's order.
- **Kotlin:** kotlin.test's `message` (after 1 or 2 values, or by name), and AssertJ's descriptions. A file that imports JUnit 4's `Assert`, as in Java, takes the message first, except in a call with a named argument (Kotlin passes no named argument to a Java method, so `message =` is kotlin.test's) and in an unqualified call whose name the file imports from kotlin.test by name, or with `import kotlin.test.*` when nothing is imported from `org.junit.Assert` (Kotlin prefers an import by name, and `import org.junit.*` brings in the class `Assert`, not its methods).
- **Swift:** XCTest's `message` (after 1 or 2 values); `#expect` and `#require`'s comment.
- **Dart:** `reason:` of `expect` and `expectLater`.
- **C#:** NUnit's and MSTest's `message` (after 1 or 2 values, `Assert.That` after 1); xUnit's `userMessage` of `Assert.True` and `Assert.False`; FluentAssertions' `because`. xUnit's `Assert.Equal` takes no message. FluentAssertions' methods that take a list of values (`BeEquivalentTo("alice", "bob")`, `NotBeEquivalentTo`, `Contain`, `NotContain`, `StartWith`, `EndWith`) are not in the table: every argument is a value.
- **C and C++:** the last argument of Unity's `…_MESSAGE` forms; Check's `ck_assert_msg` format. GoogleTest's `<< "…"` was never part of the call.

A message is the first argument at or after that place that is written as a string, with what follows it. An argument there that is not a string (a `delta`, `places`, a comparer) is a value, so it still counts.

**A call that is all message** (`pytest.fail`, `self.fail`, `assert.fail` with one argument, Go's `t.Error`/`t.Errorf`/`t.Fatal`/`t.Fatalf`, testify's `Fail`, `fail` in Java, Kotlin and Dart, `XCTFail`, `Assert.Fail`, `FAIL`, `TEST_FAIL_MESSAGE`, `ck_abort_msg`) checks what holds its expected value, when it is the branch of one: the condition of an `if` or an `elif` (`!(…)` in an `else`), the condition of a Swift `guard`, or the header of the `except` or `catch` it is in. Only blocks, statements and an `else` may lie between that branch and the call, at most six levels up. So `if got != 3 { t.Errorf("…") }` → `if got != 4 { … }` is a changed expected value, and a changed message is not. In the condition, a number that no comparison holds (`5*time.Second` in `!waitFor(t, ready, 5*time.Second)`) is no expected value and is masked; when the condition holds one, the call keeps its message, as before this ADR, since the value may be written only there (`!reflect.DeepEqual(got, []int{1, 2})` with `t.Fatalf("want [1 2]")`). A number in a comparison (`got != 3`, `add(1, 1) != 2`) and every string stay values, and a string is compared by its text, not its quotes (`status != 'ok'` and `status != "ok"` are one value). Anywhere else (a `switch` or `match` case, a loop, the test's own body, a helper) the call is compared with its message, as before this ADR: the message may be the only place its value is written, so a changed message there is still `expected-changed`.

### 3. Tests are followed through renames, moves, merges and splits

- **Moves.** A test of the base that is gone from one file and new in another changed file moved there. It is followed by nothing in its old file, and what it checks is counted where it is now.
- **Renames and merges.** Each other gone test is followed by the new test of the same file that shares the most assertions with it, by what they check with literals masked. Ties go to the two names with the longest common start and end, then to the ids. A gone test that shares no assertion with any new test is followed by none. Several gone tests that pick the same new test were merged into it.
- **Splits.** A new test that no gone test picked follows the gone test it shares the most with, when one name starts with the other (`test_totals` → `test_totals_a`, `test_totals_b`).
- **Groups.** Tests joined by these links, through any number of them, are one group: the gone tests and the new tests that follow them. Past 40,000 (gone, new) pairs in one file, no test is followed.
- **`expected-changed`** pairs a gone assertion with a new one in the same test, or within one group. What is left over, in gone and new tests that no group holds or that a group did not pair, then pairs as before this ADR, any gone test with any new one, except an assertion named lost below. So a value changed in tests whose following was not seen is still found, and the review's `upstream.calls == 1`, named lost in its renamed test, is not paired with another test's `upstream.calls == 0`.
- **What a group lost.** For each group, the assertions its gone tests had and its new tests do not are named `assertion-removed` (on the base line, `… (in <old>, renamed <new>)`, or `… (in <old>, now <new>, <new>)` for a merge or a split), up to the number the group is short. One kept as it was, or with other values (`expected-changed`), is not a loss. Nor is one reworded into a new test of the file that follows no gone test, with only literals named by variables (`assert parse("x") is None` → `bad = "x"`, `assert parse(bad) is None`); a literal changed into another is not that, so `upstream.calls == 1` stays lost beside a new test's `upstream.calls == 0`. Nor is one that moved: more of that check, without its message, outside the group now than on the base, in this file or in another changed test file. Tests excused because their subject was deleted with them stay excused.
- **Named once.** The net count (ADR 0042) matches assertions by what they check without the message, as the groups do, so a loss is not named both by the net count and in its group.

So the review's third case is one `assertion-removed`, `assert upstream.calls == 1 (in test_a_trade_holds_no_connection_while_the_gate_waits_on_market_service, renamed test_a_trade_holds_no_connection_while_the_gate_refreshes_the_copy)`, and no `expected-changed`. A test renamed, or moved to another changed file, with all it checks, is still not a finding; nor are two tests merged, or one split, with all they check. A value changed in a merge or a split is `expected-changed`.

## Consequences

- On the course project's 150 commits the first version of this ADR gave 45 findings where 0.5.1 gave 61: the 15 comment words and the 3 false `expected-changed` are gone, and two assertions that renamed tests lost are named, the review's `assert upstream.calls == 1` and `assert served[0] is served[1]` in `test_auth_client_lifespan.py`, which the review had not seen (`bench/RESULTS.md`). The later changes keep more as values and codes; that run was not repeated on them.
- `expected-changed` needs a person's approval (ADR 0046). Fewer false ones means fewer approvals asked for nothing.
- Before and after numbers on the corpus and the held-out cheats are in `bench/RESULTS.md`.

## Limits

- **Message tables are by name.** A wrapper or a framework not listed keeps its message in what it checks, as before: a changed message there is still `expected-changed`.
- **A message that is not written as a string** (a variable, `String.format(…)`, a lambda) is taken for a value.
- **A fail call outside an `if`, `elif`, `guard`, `except` or `catch`** is compared with its message, so a changed message there is still `expected-changed`.
- **A word of prose that is also a code** is read as one: `# nosec the input is ours` is `nosec:input`, and `# pylint: disable=fixme see below` keeps `fixme`. Both tools read it that way too.
- **Following is a guess.** Two tests renamed and rewritten at once may be grouped the wrong way; the effect is a misnamed `assertion-removed`. The leftover pairing keeps a changed value from being missed. The net count of `assertion-removed` (ADR 0042) is not changed by it.
- **When a group lost several assertions and is short fewer**, the ones named are the first in the file, not always the ones that went.
- **Losses are checked per test only for followed tests.** A test that keeps its name and loses an assertion while a new test of the file gains one is still covered by the net count (ADR 0042), as before. Doing the same for every kept test would name assertions moved between tests.
- The one-word pylint and bandit names are from their current lists.
- **A number compared with nothing in the `if` around a fail call is not a value.** A change to it alone (`[]int{1, 2}` → `[]int{1, 3}` in `!reflect.DeepEqual(…)`, with the message unchanged) is no finding, as in 0.5.1; with the message changed too, it is.
- **A check reworded into a new test is excused only when every change names a literal by a variable.** A rewording that also changes the call (`parse("x")` → `parse_text(bad)`) is still named lost.

## Not done

Changes the guard can still miss:

- **JUnit 4 without the import or the receiver.** A file whose message-first asserts come another way (a test class that extends JUnit 3's `junit.framework.TestCase`, a base class or a wrapper of its own) is read in JUnit 5's order, so in `assertEquals("name", actual, "alice")` the value `"alice"` is taken for the message.
- **A value written as a string where a table says message.** In the message's place, the first argument written as a string is the message, so a value there that is a string literal is left out (a wrapper or an unlisted framework whose call has the same name as a listed one and another order).
- **A pylint or bandit code of one word missing from the lists.** A pylint message or checker name of one word, or a bandit test of one word, that is not in the lists (one added in a later version) is not read as a code, so a suppression of it is missed.
- **A check counted as moved because another changed file added the same check.** An assertion a followed test lost is not named when another changed test file now holds more of the same check than on the base, even when that file's check belongs to a different test and the lost one is simply gone.
- **A test moved to another file with a value changed.** `expected-changed` compares one file at a time, as it did before this ADR, so `assert get(1) == "alice"` moved from `tests/test_api.py` to `tests/test_users.py` as `== "bob"` is no finding. The count of assertions is the same, so the net count says nothing either.

Also not done:

- No new detector. Nothing about other kinds of finding changed.
- The base run, hooks, CI and the version were not touched.
