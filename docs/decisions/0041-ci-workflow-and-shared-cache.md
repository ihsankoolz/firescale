# 0041 — The generated CI workflow and the shared step cache

Status: accepted (2026-11-13, M22). Builds on ADR 0036 (the step cache), ADR 0031 (only the default branch writes, CVE-2025-36852) and ADR 0037 (the base). Changes ADR 0019 on one point: `sync` may now replace a workflow firescale wrote, but only while nobody has edited it.

## What GitHub's docs say, read on 2026-11-13

docs.github.com was blocked by the build environment's network policy at first; the owner's environment was given access to it, and every page below was read on 2026-11-13. The actions' own files were read from their tagged sources on GitHub the same day.

1. **The cache action's current version** is v6.1.0 (`actions/cache`, `actions/cache/restore` and `actions/cache/save` ship together; tag `v6.1.0` is commit `55cc8345863c7cc4c66a329aec7e433d2d1c52a9`). Its `restore/action.yml` at that tag has the inputs `path`, `key`, `restore-keys`, `enableCrossOsArchive`, `fail-on-cache-miss`, `lookup-only` and the outputs `cache-hit`, `cache-primary-key`, `cache-matched-key`. Also pinned: `actions/checkout` v7.0.1 (`3d3c42e5…`), `actions/setup-node` v7.1.0 (`949feb24…`), `actions/setup-python` v7.1.0 (`6d4fd22b…`), resolved with `git ls-remote` on the actions' repositories. Sources: <https://github.com/actions/cache/releases>, <https://github.com/actions/cache/blob/v6.1.0/restore/action.yml>. (docs.github.com's own examples still show `actions/cache@v4`.)
2. **Scope per ref.** "Workflow runs can restore caches created in either the current branch or the default branch (usually main). If a workflow run is triggered for a pull request, it can also restore caches created in the base branch, including base branches of forked repositories." And: "When a cache is created by a workflow run triggered on a pull request, the cache is created for the merge ref (refs/pull/.../merge) … It cannot be restored by the base branch or other pull requests targeting that base branch." The search order is the current branch, then the default branch; for several prefix matches, the most recently created wins. Source: <https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching> ("Restrictions for accessing a cache", "Cache key matching").
3. **`pull_request` and `pull_request_target`.** "Only these workflow triggers can create or overwrite caches in the default branch's scope: push, workflow_dispatch, repository_dispatch, delete, registry_package, page_build, schedule. Runs triggered by any other event that resolves to the default branch are given read-only access … This includes … pull_request_target, issue_comment, and workflow_run." And: "The pull_request event is not affected. Caches created by a pull_request run are already scoped to the merge ref." `pull_request_target` "runs in the context of the default branch of the base repository … Avoid using this event if you need to build or run code from the pull request." Sources: the dependency caching reference ("Cache access for low-trust workflow triggers"), <https://docs.github.com/en/actions/reference/workflows-and-actions/events-that-trigger-workflows>. Also: "Anyone with read access can create a pull request on a repository and access the contents of a cache", so nothing secret may be cached.
4. **`cache-mode`.** A workflow-level or job-level key, "enforced with scoped cache tokens": `read` (restore only), `write`, `write-only`, `none`. Omitted, trusted triggers get `write` and low-trust ones `read`. "The runner exposes the effective mode in the ACTIONS_CACHE_MODE environment variable, and the actions/cache action and the @actions/cache toolkit honor it." Sources: the dependency caching reference ("Controlling cache access with cache-mode"), <https://docs.github.com/en/actions/reference/workflows-and-actions/workflow-syntax> (`cache-mode`, `jobs.<job_id>.cache-mode`).
5. **Size and eviction.** "GitHub will remove any cache entries that have not been accessed in over 7 days. … By default, the limit is 10 GB per repository … Once a repository has reached its maximum cache storage, the cache eviction policy will create space by deleting the caches in order of last access date, from oldest to most recent." The limit can be raised (up to 10 TB for a user's repository), billed beyond 10 GB; a budget that runs out makes the cache read-only. Uploads are limited to 200 a minute per repository, downloads to 1500. Source: the dependency caching reference ("Usage limits and eviction policy").
6. **Other facts used.** `GITHUB_BASE_REF` is "the name of the base ref or target branch of the pull request", set only for `pull_request` and `pull_request_target`; `GITHUB_WORKFLOW_REF` is "the ref path to the workflow", for example `octocat/hello-world/.github/workflows/my-workflow.yml@refs/heads/my_branch`; `GITHUB_EVENT_PATH` is the event payload (<https://docs.github.com/en/actions/reference/workflows-and-actions/variables>). For `pull_request`, `GITHUB_SHA` is "the last merge commit of the pull request merge branch" (events page). `cancel-in-progress` may be an expression (<https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency>). checkout's `fetch-depth`: "0 indicates all history for all branches and tags", default 1 (<https://github.com/actions/checkout>). setup-node's `package-manager-cache` turns its automatic cache off; setup-node and setup-python both save their cache in a post step (`post: dist/cache-save/index.js` in their `action.yml` at v7.1.0). GitHub-hosted runners set `ImageOS` and `ImageVersion` (<https://github.com/actions/runner-images>, `images/ubuntu/scripts/build/configure-environment.sh`). The package managers' download folders come from `npm config get cache` and `pip cache dir` (actions/cache `examples.md`), and `pnpm store path`.

## Decision

### The generated workflow

`core/ci-exists` (and `group-project/ci-verify`, which shares its fix) writes `.github/workflows/ci.yml` with two jobs:

- **`pull-request`** (`if: github.event_name == 'pull_request'`): `cache-mode: read`, and only `actions/cache/restore` steps. It has **no save step at all**, not a save step behind a condition, and the setup actions' own caches are off there (`package-manager-cache: false`, no `cache:` input), since they save in a post step. It runs `npx firescale verify --affected --base "origin/$BASE_REF" --jobs 2 --shared-cache .firescale/shared`, with `BASE_REF` from `github.base_ref` through `env:` (never pasted into the script).
- **`default-branch`** (`if: github.event_name == 'push'`): restores the same caches, runs a full `npx firescale verify --jobs 2 --shared-cache .firescale/shared`, then saves with `actions/cache/save`, each save only when `github.ref_name == github.event.repository.default_branch`.
- **Never `pull_request_target`.** A test checks the word is not in the file.
- **Both check out the whole history** (`fetch-depth: 0`), so the merge base with the base branch is in the clone.
- **Concurrency:** `group: ci-${{ github.event.pull_request.number || github.run_id }}`, `cancel-in-progress: ${{ github.event_name == 'pull_request' }}`. A new push to a pull request cancels its run. Each push has a group of its own (its run id), so it is never cancelled, not even while queued: a group holds one pending run, and a shared group would drop a push's run.
- **The push trigger** names the repo's default branch: `origin/HEAD` when there is a remote, else the branch of a new repo (one branch at most), else `[main, master]`.
- **Download caches** (the package manager's own cache, not `node_modules`; `hashFiles` leaves out `node_modules` and `.venv` with `!` patterns): npm (`npm config get cache`, keyed on `package-lock.json`), pnpm (`pnpm store path`, keyed on `pnpm-lock.yaml`) and pip (`pip cache dir`, keyed on requirements lists and `pyproject.toml`), restored in both jobs and saved from the default branch only when the restore was not an exact hit. Python projects that install with pip are installed with the runner's `python` (`setup-python`, `3.x` or `.python-version`); uv, poetry and pipenv projects get a note instead.
- **`--jobs 2`**: GitHub's standard Linux runners have two or more cores. A repo whose projects share a test database can edit it: the workflow is theirs once edited.
- Every action is pinned to a commit, with its tag in a comment.

### The shared step records

- **What is kept**: one small JSON record per passing step, `.firescale/shared/<key>.json`: `format`, `key`, `result` (`passed`), `time`, `durationMs`, `outputDigest` (blake3 of the step's stdout and stderr) and `writer` (`workflow` = `GITHUB_WORKFLOW_REF`, `ref` = `GITHUB_REF`, `commit` = `GITHUB_SHA`). Never a build output, never the output itself. A record is about 400 bytes.
- **The key in CI** is the step's whole M18 key, plus the bytes of the workflow file (found from `GITHUB_WORKFLOW_REF`), and `ImageOS` and `ImageVersion` through the environment allowlist (now 23 names). The cache entry's own key (`firescale-steps-<os>-<image>-<hash of ci.yml>-…`) matches, so a record is never restored under another image or workflow.
- **A record is used only when** its `key` equals the step's key exactly (a prefix or another file name is a miss), its `result` is `passed`, its `time` is within 30 days, and its `writer.ref` is `refs/heads/<default branch>`, the default branch read from the event payload (`repository.default_branch`). Anything else is ignored, and `FSCALE_LOG=cache` says why.
- **Only a push to the default branch writes records.** firescale checks the event and the ref itself; the workflow's pull request job cannot save in any case. A run that writes never reads this machine's own step cache: on a runner kept between jobs, that cache may hold a pull request's passes, and a record would vouch for them. At the end of a writing run, each record file (`<key>.json`) that may not be used is removed, temporary files a killed run left (`.<key>.<pid>.tmp`), and the oldest records beyond 2000. Nothing else is ever removed: no folder, no link, no file of another name. The folder must be one of its own: verify refuses (with a note) the repo, a folder above it, and firescale's other folders under `.firescale`.
- **"A run never uploads what it restored"**: the save key ends with the hash of the records (`hashFiles('.firescale/shared/*.json')`), and the save step runs only when that hash differs from the end of the key the restore matched (`cache-matched-key`), as the save action's README advises ("To avoid saving a cache that already exists, the `cache-hit` output from a restore step should be checked"). When the run added nothing, nothing is uploaded. When it added records, the new entry holds the restored ones that passed the checks above plus the new ones, so the default branch's cache grows instead of losing every project that did not run. Everything in it was written from the default branch.
- **What the writer field is.** It is a label, not a proof: whoever can save a cache entry can write any `writer`. What keeps a pull request from planting a result is GitHub's scoping and the token: a pull request's caches are scoped to its merge ref, which the default branch and other pull requests never restore, and its job in this workflow cannot save at all. A pull request that adds a workflow of its own can save into its own merge ref and so fool only its own check, which is no more than editing `ci.yml` would do, in plain sight in its diff. A stacked pull request also restores its base branch's scope, which only people who can push there can write. The writer check catches records saved by mistake from other branches, and makes every record say where it came from.
- **Laptops do not read the shared cache.** Outside GitHub Actions (`GITHUB_ACTIONS` is not `true`) `--shared-cache` does nothing but say so. See "Later".

### The base in a shallow clone

When `--base` names a commit but the clone is shallow and does not hold the merge base, verify no longer stops with a usage error: there is no base, `--affected` runs every project, and a note says to fetch the full history (`actions/checkout` with `fetch-depth: 0`).

### `sync` and a workflow firescale wrote

A workflow a person wrote is never rewritten. `core/ci-exists` reports a low-severity, deterministic finding, and its fix replaces `.github/workflows/ci.yml`, only when the file is tracked and is exactly as firescale wrote it: either byte for byte one of the starters of firescale 0.1.0 to 0.3.0 (one text per install variant, line endings aside), or a new workflow whose last line, `# firescale-workflow: <digest>`, matches the digest of everything above it. One edited character and the file is the team's.

A `--base` that names nothing is still a usage error, shallow clone or not.

## After the review

An independent review before the pull request found, all fixed with tests: pruning removed every non-record entry, folders included, so `--shared-cache .` on a default-branch push deleted the checkout (now only record and temporary files are ever removed, and the repo, a folder above it and firescale's other folders are refused); the push trigger assumed `main` or `master`; pushes shared a concurrency group, so a queued push's run could be dropped; a record's commit could panic the summary; a mistyped `--base` in a shallow clone read as shallow; `hashFiles` walked `node_modules`. It also found that the writer field was described as a defence; the text above now says what it is.

## Why not

- **One job with a condition on its save step**: the pull request job would hold a save step; a mistake in the condition writes the cache. Two jobs, and `cache-mode: read`, make it impossible rather than unlikely.
- **The setup actions' `cache:` input in the pull request job**: their post step saves. With `cache-mode: read` the save would be refused, but the job would still hold a save.
- **Records kept per pull request**: they could never be trusted by the default branch (scoped to the merge ref), so they would only cost storage.
- **Uploading only the new records**: the next restore would get only the last push's records, and every other project would miss.

## Later

- Laptops reading the shared cache (through the GitHub API, with a token), so a teammate's first run after a pull is warm. Not now: it needs a token on every machine and a way to verify who wrote a record that does not rest on the cache's scoping.
- A config key for `--jobs` in the generated workflow, and caches for yarn, bun, uv and poetry.

## Consequences

- A pull request runs only the projects it reaches, and steps whose key matches a record written from the default branch do not run at all.
- A step that passes on the default branch and is unchanged on a pull request costs a restore of a small folder, not a run.
- The workflow is longer (two jobs of about 30 lines). Repos made before M22 keep their old workflow until `fscale sync` runs, and only if it is unedited.
- Proof: `shared-cache.test.ts`, `sharedcache::tests`, `core::ci_exists::tests`, the `init` snapshots in `scaffold.test.ts`.
