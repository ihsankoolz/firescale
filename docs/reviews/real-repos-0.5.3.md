# fscale on 15 real public repos

Date: 2026-11-17 (UTC). Workflow: `.github/workflows/real-repos.yml`, [run 44133697663](https://github.com/ihsankoolz/firescale/actions/runs/44133697663) on `main` at `fff15d1` (0.5.2 plus docs and workflows; no code of `fscale` differs from the tag `v0.5.2`). GitHub's `ubuntu-latest` and `macos-latest` runners, release builds. Every output is an artifact of the run, kept 30 days.

Each job installed one repo's toolchain, cloned the repo at a pinned commit with no remote kept, and ran, in this order: `fscale doctor`, `facts --json`, `graph --explain`, `check`, `verify --dry-run`, `verify --budget 15m --json`; then the repo's own test command; then `fscale verify --no-cache --json` again. Nothing of these repos is committed here, and nothing was pushed to them.

## Summary

- **`fscale verify` has now run real commands in every ecosystem M31 to M35 claim.** Swift (`swift test`, `swift format lint`), Xcode (`xcodebuild build`), .NET (`dotnet format`), Flutter (`flutter analyze`), Dart (`dart analyze`, `dart test`), Go, Maven, Gradle with Kotlin, Gradle with Android, and CMake with `ctest`.
- **It has still never run `dotnet test`, `flutter test` or `xcodebuild test` on a real repo.** In both .NET repos and in the Flutter repo the lint step failed first, so the test step was not started. Xcode tests need a simulator that a person names (ADR 0051), so that step is skipped by design.
- **Detection was right in all 15**: the ecosystem, the project folders and the commands are the ones a person would name, with the notes in the table.
- **The result was right in 8 of 15, wrong in 6, and not judged in 1** in the first run; after three fixes it is 9, 5 and 1 (see "The second run, after three fixes"). The 6 wrong results have three causes: a lint command fscale guessed that the repo does not hold itself to (4 repos), packages not fetched read as a lint failure (1), and one Maven repo whose README names `mvn clean verify` (1).
- **No bug was fixed in the first run; three were fixed after it** (bugs 2, 3 and 5), and the 15 repos were run a second time: see "The second run, after three fixes". The table below is the first run's and has no "after" column. Each bug is listed below with what a failing test would show.

## Bugs: three fixed since (2, 3 and 5), two not

1. **A lint command the repo does not hold itself to fails, and then the tests are not run.** fscale picked `dotnet format --verify-no-changes` for both .NET solutions, `swift format lint --strict` where a `.swift-format` file is, and `flutter analyze` (which exits 1 on `info` lines) for the Flutter packages. In 4 of 15 repos that step fails on code the repo's own CI accepts, and `verify` says `FAILED` without running tests that pass. Blame-aware verify does not help on a first run on the default branch: there is no base. A failing test would be a fixture with a `.sln` and unformatted code whose `dotnet test` passes: today the test step is `not-run`. **Needs your decision**, not only a fix: whether a guessed linter with no sign that the repo uses it (no CI step, no script) should be a step at all, should report without blocking, or should never keep the test step from running.
2. **Fixed after this review (seen again only where the second run below says so).** **Dart and Flutter packages that are not fetched read as a failed lint.** `dart analyze` before `dart pub get` fails with `undefined_function`, and verify reports `FAILED`, not `SETUP NEEDED`. Doctor said `OK` and named no dependency check for Dart. A failing test: a Dart fixture with a dependency and no `.dart_tool/package_config.json`; doctor should name `dart pub get`, and verify should say setup needed.
3. **Fixed after this review for SwiftLint only (seen in the second run).** **Doctor did not look for the linter verify will run.** In SwiftyJSON verify ran `swiftlint lint --strict` and said `the program swiftlint was not found on the PATH`; doctor, seconds earlier, said the machine was ready. A failing test: a fixture with `.swiftlint.yml` and no `swiftlint` on the PATH; doctor should have a line for it.
4. **`mvn -B test` was the test command for a Maven build whose modules test each other's packaged jars** (gson). The repo documents `mvn clean verify`. Not shown here that `mvn -B verify` passes. A fix would need a rule for when `verify` is the right phase; `verify.test` already lets a repo say so.
5. **Fixed after this review (seen in the second run).** A folder that holds a `CMakeCache.txt` is no longer searched for projects. **A CMake build folder with another name than `build` was read as a project.** After the workflow's own command built fmt into `build-own`, fscale found a Make project there and ran `make test` in it (it passed). The folder was this workflow's doing, but `cmake-build-debug` and `out/build` are common names. A failing test: a CMake fixture with a generated `Makefile` and `CMakeCache.txt` in `cmake-build-debug`; facts should list one project.

## Limits

- **One commit per repo, 15 repos, two runs** (the second after three fixes; the verdicts in the table are from the first). Two per ecosystem at most. A repo was picked for being small or medium and well kept; that is not the mix of real projects.
- **"Right" was judged by an AI from the outputs**, by comparing with the repo's own test command in the same job. For gson, SwiftyJSON and the Xcode build that command is not the same thing fscale ran, as the table says.
- **Each repo's own test command is its ecosystem's usual one.** Only for the repos fscale got wrong were the repo's CI files or README read (GuardClauses, serilog, provider, swift-argument-parser, gson).
- **`--budget 15m` left nothing out anywhere.** It leaves out only steps with a kept time, and every repo was new to the machine. It is refused in CI (ADR 0057), so the workflow takes `CI` and `GITHUB_ACTIONS` out of that command's environment.
- **macOS:** the Xcode job and one Swift job were cancelled by GitHub after 15 minutes without a runner, and passed when run again. Windows was not run.
- **Not run through fscale on any real repo, still:** `dotnet test`, `flutter test`, `xcodebuild test`, and anything for Meson, Make alone, or SwiftPM on Linux.
- Toolchain versions are whatever the runner and the setup actions gave on that day (Swift 6.3.3, Xcode 26.6, Flutter 3.50.0, Dart 3.14.1, CMake 4.4.5, Java 21 from the setup action). provider's failure depends on that Flutter version.
