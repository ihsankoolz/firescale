# 0064 — The command the stop hook starts, and what the hook files affect

Status: accepted (2026-11-16, for 0.5.2; revised the same day after the review of the pull request, and again after its second review). Changes ADR 0014 on one point: the default of `hooks install --bin` was `fscale`. Changes the command `fscale_command` gives (ADR 0027) where a repo has no fscale of its own: `npx firescale` becomes `npx --yes firescale@<version>`, in the hook, the `agent-ready/verify-hook` fix, the AGENTS.md block and the agent permissions. Narrows ADR 0036 (every file that belongs to no project is in every step's key) and ADR 0032 (such a file affects every project) for three files, the way ADR 0058 did for `firescale.config.json`. Adds a section to `fscale doctor` (ADR 0026), whose JSON format becomes version 2.

## Context

Two findings of the 0.5.1 run on the course project (`docs/reviews/cs464-0.5.1.md`):

- **Finding 6.** In a clone of the course project (no root `package.json`, `fscale` not on the PATH), `npx firescale@0.5.1 hooks install --all` wrote `fscale hooks run --agent <name>` into the three hook files and said "Each agent now runs ...". Run by hand, `cmd /d /s /c "fscale hooks run --agent claude"` gave `'fscale' is not recognized as an internal or external command, operable program or batch file.` and exit 1. A stop hook that exits 1 lets the agent stop: verify never ran, and nothing said so.
- **Finding 5.** In the same copy, after `hooks install --all`, `verify --affected --json` gave `"reason": ".claude/settings.json belongs to no project"` for all six projects. The files firescale had just written ran every project, a 1 h 40 min run on that repo, until they were committed. The same finding reports an untracked `verify.log` at the root doing the same.

The owner asked for five things: a command that starts where `fscale` is not on the PATH, on Windows too; a check at install that says plainly when it cannot start; a stop hook that cannot start must never look like a pass, with what each agent does written down from its own docs; a decision on whether the hook files can change a step's result; and no change for `*.log`, only an entry under "Needs your decision" (the owner then chose `core/gitignore-basics`, section 5).

The review of the first version of this pull request (fixtures `fixA`, `fixC` and `fixD`) found that it went too far for the hook files and trusted too much in the check:

- A project whose test reads the hook file (`require('../.claude/settings.json')` in `web/test.js`, a shared node `.claude` in the graph) kept its cached pass after the file changed, `--affected` ran `0 of 2` projects, and blame-aware verify on a branch said `pre-existing` for a test that passes on `main`.
- Claude Code gives the `env` of `.claude/settings.json` to every command it starts, the stop hook's verify among them. A change of `env` ran nothing.
- Run through npx or a package script, fscale has `node_modules/.bin` first on its PATH: `--bin fscale` "started" there and nowhere else.
- The check started the text before `hooks run --agent <name>` from a hook file already in the repo: `echo ran-from-repo-file > pwned.txt & npx firescale hooks run --agent cursor` created `pwned.txt`.
- The check took any one word that starts with a digit for firescale's version: `--bin npx` passed with npm's version.
- The owner decided to pin the default, and asked for `fscale doctor` to check the hook on any machine.

So in all three agents a stop hook that cannot start lets the agent stop, as fscale's own exit 1 does on purpose. In Codex, a project hook that is new or edited does not run at all until the person trusts it; Codex warns at startup.

## Decision

### 1. Without `--bin`, the repo decides the command, pinned

`hooks install` writes the command `fscale_command` gives, the one the `agent-ready/verify-hook` fix, the AGENTS.md block and the agent permissions use too (ADR 0027):

- the root `package.json` has an `fscale` script: `pnpm --silent fscale`, `yarn --silent fscale`, `bun run --silent fscale`, or `npm run --silent fscale --`, by the repo's package manager;
- the root `package.json` lists `firescale` in `devDependencies` or `dependencies`: the fscale it installs, `pnpm exec fscale`, `yarn --silent fscale`, `bun run --silent fscale` or `npx --no -- fscale` (`--no` fails instead of downloading; `--` ends npx's options, see section 6);
- otherwise `npx --yes firescale@<version>`, with the version of the fscale that runs (`firescale_core::version()`), so a version bump changes it with no other edit. `pinned_npx` builds it; it is the form of the CI tamper step (ADR 0045).

A command given with `--bin` is written as it is, unchanged. `fscale_command` lives in `firescale_core::hooks`; `crates/rules/src/agent-ready/managed.rs` re-exports it.

Why:

- **Not this machine's PATH.** The hook files are committed; the person who runs `hooks install` is one of several machines that will start the command. A default that depends on the installer's PATH would write a command that works for them and not for a teammate, which is finding 6 the other way round.
- **Pinned (the owner's decision).** Measured by the reviewer: unpinned `npx firescale` asks the registry on every start whether `latest` changed, and runs `latest`. So a release of firescale silently changes every teammate's hook, and since the version is in every step's key (ADR 0036), it empties every cache key at once. A pin moves only when someone runs a newer fscale on purpose. `--yes` is written although npm assumes it when stdin is not a terminal: it is the tamper step's form, and costs nothing.
- **npx starts wherever Node.js is installed,** on Windows too (`npx.cmd`, and the `npx` script Git Bash finds).
- **What npx costs.** Measured on the owner's Windows machine while other builds ran: `npx --yes firescale@0.5.1 --version` and `npx --yes firescale --version` each took 7 to 10 s per start once firescale was in npm's cache. Both started with `--offline` once cached; an uncached version with `--offline` stopped with `ENOTCACHED`. The first start on a machine downloads firescale (one package and its native binary). Inside a stop hook that runs verify the start is a small part; a repo that wants it faster adds an `fscale` script, installs firescale, or passes `--bin`.
- **An installed pin follows the version through `sync`, and only through it** (the owner's decision; section 7). A hook counts as installed whatever comes before `hooks run --agent <name>` (ADR 0014), so `hooks install` leaves an old pin in place; `fscale sync` moves an older pin firescale wrote and says so. The check after installing and `fscale doctor` say when the hook answers another version than the fscale that runs. The AGENTS.md block and the permissions follow the version too: they are rewritten whole by `sync`.

### 2. The command is started, safely, and the result said plainly

After the files are written, `hooks install` checks the stop hook of each file that holds it (written now or already there; a refused file is skipped). `fscale doctor` does the same check on whichever machine runs it, in a section `Agent hooks` (`hooks` in `--json`, whose `schemaVersion` becomes 2 for the new section value): `ok`, `warning` when it answers another version, `PROBLEM` (exit 1) when it cannot start. The check:

- **Starts only a command fscale writes.** The text before `hooks run --agent <name>` in a hook file came from the repo. It is started only when it equals the command this run writes (the default or `--bin`), the repo's default, or a pin any release wrote (`may_start`, `pinned_version`: `npx --yes firescale@` and a version of letters, digits, `.`, `-` and `+` only); doctor has no `--bin`, and starts less (section 6). Any other command is printed with the instruction to read it and run it by hand, and not started: `The hook in .cursor/hooks.json was not started: it runs ..., which is not the command fscale writes here (...), and fscale starts no other.` `hooks install` then exits 1, doctor gives a warning. (The review's `echo ... > pwned.txt & npx firescale hooks run --agent cursor` is now printed, not run.)
- **Asks something only firescale answers.** It runs `<command> --version --json`. Since this version, `fscale --version --json` prints `{"name":"firescale","version":"<version>"}`; plain `--version` is unchanged. One start answers both "is it firescale" and "which version", where a second probe (`hooks run --help` for the name, then `--version`) would double the 7 to 10 s an npx start costs. Anything else is "not firescale's answer": npm's `10.9.2` for `--bin npx`, a usage text, nothing, or a firescale before 0.5.2 (which prints only its version), and the message says so.
- **Starts it the way an agent does:** in the repo root, through `cmd /D /S /C` on Windows and `sh -c` elsewhere (the shell doctor uses), with stdin closed, for up to 120 s, and with `CLAUDE_PROJECT_DIR` set to the repo root when the command is in Claude Code's file (Claude Code sets it for its hooks). Each distinct command is started once.
- **Without the launcher's PATH folders.** The folders a package manager puts first for its own run are left out (`launcher_folder`): `node_modules/.bin` of the repo root or of a folder above it, npx's `_npx/<hash>/node_modules/.bin`, the `dlx`, `dlx-*` and `bunx-*` download folders, and `node-gyp-bin`. The stderr line names them. An agent started from a terminal does not have them. A repo's own `pnpm exec fscale` still works: pnpm adds the folder itself. The first version left out every folder inside a `node_modules`; on CI that dropped `~/setup-pnpm/node_modules/.bin`, where `pnpm/action-setup` puts pnpm, which an agent's PATH has too (section 6).
- **Says first what it runs,** on stderr: ``fscale: checking that the hook can start: running `npx --yes firescale@0.5.2 --version --json` in the repo root, as an agent would.``, then `npx may download firescale from the npm registry first.` for `npx`, `npm exec`, `pnpm dlx`, `yarn dlx`, `bunx` and `bun x` (named by the tool, not with `npx --no`), `It runs the fscale installed in this repo's node_modules.` for `pnpm exec fscale` and `npx --no -- fscale`, or ``It runs this repo's own `fscale` package script.`` for `npm run`, `pnpm`, `yarn` and `bun run` with the script `fscale` (`npm exec` is not called a package script).
- **Answers plainly:** ``The hook starts on this machine: `...` answered firescale 0.5.2.``, with `That is not this fscale (0.5.2): the agent will run firescale 0.4.0.` when the version differs; or `The hook cannot start on this machine: ...` (a non-zero exit with the last 10 lines it printed, not firescale's answer, no answer within 120 s, a shell that does not start), one paragraph on what that means and what to do, and exit 1. A refused file still gives 2. The files are kept: the command may start on a teammate's machine.

Why start it rather than look for the program on the PATH: `npx` on the PATH does not mean firescale resolves, `npx fscale` is another package, and a package script needs the repo's dependencies. Starting it answers all three. Why allow the download rather than `npx --no`: the agent's first stop would download it anyway, inside a hook with a time limit; doing it at install moves the wait, and any failure, to a moment the person is watching, and the stderr line says it before it happens.

The check is close to the agent's start, not the same: Claude Code runs Git Bash or PowerShell on Windows, Codex the session's shell, Cursor PowerShell; an agent started from a desktop app may have another PATH than the terminal; and Codex does not run an untrusted or edited project hook at all.

Tests stand in for `npx`, `pnpm`, `yarn`, `bun`, `bunx`, `npm`, `fscale` and a `--bin` command on a PATH the test builds (`hooks.test.ts`, "the command the hook starts" and "fscale doctor and the agent hooks"): the folders of this machine's PATH that hold an `npx` or an `fscale`, or that are inside a `node_modules`, are left out, and on Unix a folder with a link to `/bin/sh` comes first. No test downloads anything.

### 3. A stop hook that cannot start: caught by the check and doctor, not wrapped

After install, a hook that stops starting (npx removed, no network for a first download, a package script before `pnpm install`) still lets the agent stop: Claude Code shows a hook error notice, Codex a failed hook run, Cursor a line in its Hooks output channel (table above). `fscale doctor` finds it on any machine. The owner's example was a command written so that a failed start blocks, while fscale's own exit 1 keeps its meaning. No runtime wrapper is written:

- **A shell-form command has no common syntax.** The same committed `.claude/settings.json` runs under `sh` on a Mac and Git Bash or PowerShell on Windows; Codex's under the user's shell or `cmd`; Cursor's under PowerShell on Windows. "Run it, and exit 2 if it did not start" has no syntax common to `cmd`, Windows PowerShell 5.1 and `sh`: `||` is not valid in Windows PowerShell 5.1, `1>&2` is not valid in PowerShell, and `;` does not separate commands in `cmd`.
- **A launcher's failure and fscale's release share exit 1.** npx exits 1 for its own errors (`could not determine executable to run`, `ENOTCACHED`), the code fscale uses on purpose to let the agent go (ADR 0014).
- **A wrapper's block has no loop guard.** The count of blocks in a row lives in fscale, which did not start. The agent would be sent back with a message it cannot act on ("Claude can't repair a hook that won't run"), up to the agent's own cap: none found for Codex. ADR 0014 holds that a broken tool must not trap an agent.

The first version of this ADR said no wrapper was possible at all. That was too strong for Claude Code: its **exec form** (`"command": "node", "args": [...]`, no shell, a real `.exe` needed on Windows, so `node` and not `npx`) makes a small launcher possible. A script run by `node` would start fscale, turn a launch failure (a spawn error, or 127 or 9009 with nothing from fscale) into exit 2 with a message, and pass every other code through, so ADR 0014's exit codes stay. Its costs: it needs a Claude Code version with exec form (the version is not stated: unverified); it serves Claude Code only; a launch through npx that fails with `ENOTCACHED` exits 1 like fscale's release, so the launcher would have to read npx's output to tell them apart; it is one more file in every repo; and its block has no fscale loop guard, only Claude Code's own cap. It was listed under "Needs your decision" as the option.

**The owner's decision: no launcher.** A stop hook that cannot start does not block the agent. The check after `hooks install` and `fscale doctor` are the answer. Closed. fscale's own exit codes are unchanged.

**Decision.** Only what firescale writes is set aside; everything else stays in every key, by value (the ADR 0058 way). The first version set aside the whole `hooks` key; the second review showed why that was too much (section 6):

- **What a hook file holds apart from what firescale writes in it** (its stop hook entry, a command holding `hooks run --agent <name>` under `Stop`, or `stop` for Cursor, and Cursor's `"version": 1`) is in every step's key, by value: `hooks::outside_hooks` removes those, then the groups and event lists left empty, sorts the keys, and drops the spacing, so the order and the indentation do not count. An absent file counts as `{}`, so a file that holds only hook entries, as `hooks install` writes it on a repo without one, changes no key. A file that is not a JSON object counts by its bytes, the old whole-file rule. The step cache reads the three files from disk at each snapshot, whether or not git lists them.
- **The file itself** is a file of a unit whose folders hold it (`stepcache::covers`, checked before the hook-file rule): the repo root's own steps, a project at the root, a folder the graph cannot place, and a project that depends on a node of the graph that holds it (the shared node `.claude` of fixture `fixA`). For every other unit only the part outside the hook entries is in the key.
- **Blame-aware verify** (`same_on_base`): a changed hook file is a difference for every unit, whatever changed in it, so a failure is never labelled `pre-existing` from the files alone; the base run decides. It costs a base run of the failing steps on a branch that edits a hook file. The base result's key holds the base's hook files for every unit.
- **`verify --affected` and the stop hook** (`hooks::hook_file_changes`, `verify_plan` in `crates/cli/src/main.rs`): each changed hook file is compared with the base commit (the merge base with `--base`, else `HEAD`), outside its hook entries:
  - changed outside them, or no base to compare with: every project runs, with the reason `.claude/settings.json changed outside the stop hook entry firescale writes, and what is there reaches every step (Claude Code gives its env to every command it starts, and another hook can set that env)`;
  - changed only inside them, and a node of the graph holds it: a changed file of that node, as any other (`web` runs, `api` does not);
  - changed only inside them, and no node holds it: settled, as before: a changed file of the repo root project only, never "belongs to no project", and `configkey::mark_file_readers` runs every other unit whose scope holds the root, or a note says nothing at the root reads it: `3 changed files (.claude/settings.json and 2 more) are agent hook files, which only a step that can read every file of the repo could read, and no such step runs here, so they run nothing; the check still covers them.`

Not on the list, and still in every key and affecting every project like any file no project owns: any other file under `.claude/`, `.codex/` or `.cursor/` (`settings.local.json`, `.claude/hooks/*.sh`, the skills `agent-skills` writes, `.codex/config.toml`, `.cursor/cli.json`), and these three names inside a project's folder, which are that project's.

The cache format stays 2. Every key gains the three lines of what is outside the hook entries, so every kept pass misses once after this version, as after any version change (the version is in the key).

### 5. A stray `.log` file at the root: ignored by git, not "runs nothing"

An untracked `verify.log` at the course project's root ran all six projects (finding 5), as documented: a file no project owns runs everything. `*.log` is not added to the "runs nothing" list. A log can be read by a test (a fixture, a parser's sample) or written by a step and then read by the next, so it can change a result. **The owner's decision:** `core/gitignore-basics` writes `*.log`, so git ignores a stray log and it is no change at all. That is its own pull request of the 0.5.2 run; nothing in this one changes for it.

### 7. `sync` moves a pin firescale wrote (the owner's decision)

`fscale sync` (and `sync --check`, which reports it and exits 1) moves the version of a stop hook command that is exactly `npx --yes firescale@<version> hooks run --agent <name>`, the form firescale writes, to the version of the fscale that runs, in `.claude/settings.json`, `.codex/hooks.json` and `.cursor/hooks.json` at the repo root. It says so under the heading `agent hooks`: the file it edits, and the note `<file>: the stop hook firescale wrote ran firescale <old> (...); sync moves its pin to firescale <new>. sync changes no other command.` It never changes any other command: not one with more text after it (`... --budget 60`), not an unpinned `npx firescale` or a package script, not another hook. Only the version's text changes in the file, so every other byte stays.

Decided on the owner's behalf:

- **Only forward.** A pin newer than the fscale that runs is left as it is: a teammate's older fscale must not move the repo back.
- **Whatever packs are on.** `agent-ready/verify-hook` is not in the `core` pack that `adopt` turns on, so a rule fix would never reach the course project's hooks; the move is a step of `sync` itself, before the rules run.
- **Unsure means unchanged.** A file that is not JSON, a hook file that is a symbolic link, and a command whose exact text also stands elsewhere in the file (another hook running the same text) are left as they are.
- `hooks install` still never changes a command that is installed; it says which version the hook runs. A hook firescale 0.5.1 or older wrote (`fscale hooks run --agent <name>`, `npx firescale ...`) is not a pin: it is not started, and `hooks install` and doctor say how to replace it.
- **Known limits.** `sync --check` works on a scratch copy of the repo, which holds no git-ignored file and, on Windows without the right to make links, holds a symbolic link as a plain file: for a git-ignored hook file `--check` says nothing and `sync` moves the pin; for a linked one `--check` reports a move that `sync` does not make.

## Consequences

- In a repo with no root `package.json`, `hooks install` writes `npx --yes firescale@<version> hooks run --agent <name>` where it wrote `fscale hooks run --agent <name>`; AGENTS.md says `npx --yes firescale@<version> verify` and the permissions allow `npx --yes firescale@<version> verify *` and the like. A repo with an `fscale` script gets that script, and one that installs firescale gets that. A person who relied on the old default passes `--bin fscale`.
- Each release changes the AGENTS.md block and the permissions of such a repo: `fscale sync` rewrites them. It does not rewrite an installed hook.
- `hooks install` and `fscale doctor` start a program: npx (which may download firescale), a package script of the repo, the fscale it installs, or the `--bin` command. They say so on stderr first, start nothing else, and say plainly when it does not start.
- `fscale --version --json` prints `{"name":"firescale","version":"..."}`. `fscale doctor --json` is format version 2, with the section `hooks`.
- An agent whose stop hook cannot start still stops without verify having run; the check, doctor and `docs/hooks.md` make that visible, the agents only show their own hook error.
- After `hooks install` on a repo with no root project, `verify --affected` and the stop hook run nothing for the three files, and a full verify takes every project's pass from the cache. A change of `env`, `permissions` or any other key outside the hook entries runs every project and is in every key. A project that reads a hook file through the graph runs again when it changes.
- **Snapshots changed on purpose:** `hooks.test.ts.snap` (the pinned command, and the check's lines), `cli.test.ts.snap` (the help: `--bin`'s default and `--version [--json]`), `agent-files.test.ts.snap` (the pinned command in the hook files, the permissions and AGENTS.md), `doctor.test.ts.snap` (`schemaVersion` 2).
- **Known limits.** The check uses `cmd` or `sh`, not the agent's own shell, and the PATH of the terminal, not the agent's. A hook command that starts only inside an agent's environment (a variable it sets) is reported as not starting. A test that reads a hook file by a path the graph does not see, or through a symlink inside its project that points at the file, is not run again under `--affected` when only firescale's entry changes: `--affected` sees only the settled root file. The step cache does catch it: it hashes a symlink's target bytes (`stepcache.rs`, the file hashing), so a full run reruns that project. `hooks install` does not move an installed pin; `sync` moves it only forward and only in firescale's exact form. A Codex project hook that is new or edited does not run until it is trusted in Codex, and neither check can see that. A `.claude/settings.json` that git ignores, and `.claude/settings.local.json` (git-ignored by Claude Code's default): a change of their `env` runs nothing under `--affected` and in the stop hook, since git lists neither; a full verify catches it (the local file is in every key as a file no project owns, an ignored one is read from disk). The way to fix it is the record ADR 0058 keeps for an ignored `firescale.config.json` (`stepcache::ignored_config_changed`): compare with what the last passing run saw. Not done in 0.5.2.
