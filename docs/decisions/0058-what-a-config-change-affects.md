# 0058 — What a change to the firescale config affects

Status: accepted (2026-11-15, for 0.5.1). Narrows one rule of ADR 0031 and ADR 0032 (the firescale config affects every project), one of ADR 0036 (the config is a root file, so it is in every step's key) and the note of ADR 0043 (a config change alters every key). ADR 0034, ADR 0037, ADR 0041 and ADR 0056 are unchanged in what they decide; this ADR says how each meets the new rule.

## Context

The owner ran 0.5.0 on the course project on Windows: six projects, one whose tests take 1 h 40 min. The repo had an untracked `firescale.config.json` that set two test timeouts and nothing else. `verify --affected` ran all six projects, and every step's cache key changed.

Two rules did that:

- `graph::widening_reason` (ADR 0032): a changed `firescale.config.*` at the root affects every project.
- `stepcache::covers` (ADR 0036): the config is a file at the root that no project owns, so its bytes are in every step's key.

Both treat the config as a file. But firescale is the only reader of most of it, and it knows what each setting does. A time limit cannot make a step pass or fail differently; a command can.

## Decision

### The rule

A step is affected by a config change, and its cache key changes, only when a setting changed that can change its result. A step's result here means: whether it passes, its per-test results, the label blame-aware verify gives it, and anything a cache stores about it (the local step cache, the shared CI cache, the base-result store, the `fixed` pairing).

Settings are compared by **value, as this version resolves them**, not by the bytes of the file. So reordering keys, adding white space, or writing a default out in full (`"failOnSkipped": false`, `"packs": ["core"]`, `"rules": {}`, a key set to `null`) changes nothing for a step the next section does not name.

When unsure, a setting stays in the key.

### Where the config is still a file

The by-value rule holds only for a step whose scope does not contain the repo root: a project in a folder below the root that uses nothing at the root.

A step that runs in the folder that holds the config can read it as a file. `prettier --check .`, a JSON linter or a spell checker at the repo root reads `firescale.config.json` like any other file there, so reformatting it changes that step's result. For these units the config stays an ordinary file (`Scope::holds_root` in `crates/core/src/stepcache.rs`):

- the repo root's own steps;
- a root project (a project whose folder is the repo root);
- a folder named only under `verify.projects`, or one the graph cannot place, whose key covers the whole repo;
- a project that depends on one of those.

For them:

- the config's bytes are in the step's key, so any change to the file, white space included, runs the step again;
- the config is a changed file of that unit under `verify --affected` and in the stop hook;
- blame-aware verify treats a byte change of the config as reaching the step (`StepCache::same_on_base`): the step is not "the same on the base".

The settings every step shares are in these keys too, as in every other.

The first version of this ADR took the config out of every key. A review proved that wrong: with a root project whose lint reads the config, an untracked config written on one line failed the lint in a fresh run, yet the kept pass was served and `--affected` ran nothing. See "After the review".

### The mechanism

Three values are made from the config after it is loaded (`crates/core/src/configkey.rs`):

1. **The plan.** `plan_verify` already turns the step and project settings into one command, or `off`, per step. A step's command is in its key (ADR 0036), so a changed command is a changed key with no new code.
2. **The other settings** (`VerifyConfig::other_settings`): the raw config value with the top-level keys `$schema`, `protectedPaths`, `agent` and `verify` taken out, as JSON with the keys of every object sorted. It is made by taking out what is known, so `packs`, `rules` and any top-level key added later are in it without anyone listing them. A top-level key set to `null` counts as left out, `packs` left out is `["core"]` and `rules` left out is `{}`, as the config reader takes them. Nothing inside a rule's options is touched: a custom rule may tell `null` from absent.
3. **The settings every step shares** (`configkey::shared_settings`): a digest of the other settings and the resolved values of `verify.ci`, `verify.failOnSkipped`, `verify.stopWhenServiceDown` and `verify.stopAfterErrors`. It is a new line of every step's key.

`firescale.config.json` itself is no longer one of the files of a key whose scope does not contain the repo root (`stepcache::covers`); it stays a file of every key whose scope does. The key recipe changed, so the cache format is 2 and passes kept by 0.5.0 are not read.

The function that makes the shared digest takes `VerifyConfig` apart field by field with no `..`, so a new field does not compile until someone puts it on a side. A unit test walks the table above, changes each setting, and checks the side it lands on.

### `verify --affected` and the stop hook

`--affected` compares the commit it measures from (the merge base with `--base`, or `HEAD` when there is none) with the working tree. Firescale reads the config **at that commit** (`git show <commit>:./firescale.config.json`) and compares it with the loaded one. It does so whether or not git lists the file as changed: git lists a config it ignores nowhere (see "A config that git ignores").

- The shared settings differ: every project is affected, as before. The reason names the config.
- Otherwise the two plans are made from the same facts, once with each config (`configkey::effect_between`). A project (or the root) is affected when one of its steps has a command now that it did not have, with that exact text, at the base. It is also affected when a step that was off at the base is now **skipped** because no command was found for it: nothing runs for that step, but the run must count it, since a skipped step makes the run partial, or failed with `verify.failOnSkipped`. The reason names the steps: `firescale.config.json changes what its test step runs`.
- Otherwise no setting reaches a step.

The config file is then no longer "a file no project owns": it counts neither as a widening file nor as an inert one. As a file it is a changed file of the root project, when there is one (`graph::affected_except`), and it runs every other unit whose scope contains the repo root (`configkey::mark_file_readers`). The reason of a root project is `changed: firescale.config.json`; of the others, `firescale.config.json changed, and these steps can read every file of the repo, the config among them`. Projects in folders below the root are not affected by the file.

When no setting reaches a step and no unit of the plan can read the file, the change affects nothing. A note says so, so nobody wonders why nothing ran.

The stop hook is `verify --affected` from the base commit, so the same holds there.

| The config is...                                                       | What happens                                                                                                                                                                                                                         |
| ---------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **added**, tracked, **untracked** or **ignored by git**                | The base has none, so the base's settings are the defaults (the same as an empty `{}`). The new config is compared with the defaults, setting by setting. A new config that only sets time limits affects no project below the root. |
| **removed**                                                            | The working tree's settings are the defaults; the base's are read from the commit.                                                                                                                                                   |
| **changed**                                                            | Compared setting by setting.                                                                                                                                                                                                         |
| **renamed between `.json` and `.ts`**                                  | A `.ts` file is among the changed files, so every project is affected (below).                                                                                                                                                       |
| **not valid JSON, or not a valid config, in the working tree**         | Unchanged: every command that loads the config stops with exit 2 before any step.                                                                                                                                                    |
| **not valid JSON, or not a config this version can read, at the base** | Every project is affected. The reason says the base's config could not be read.                                                                                                                                                      |
| **of a newer shape**                                                   | See below.                                                                                                                                                                                                                           |

### A config that git ignores

Git lists an ignored file nowhere: not among the changed files, not among the untracked ones, and in no commit. So nothing above may depend on git listing the config.

- **Its settings.** The config is compared with the comparison commit's whether or not it is among the changed files (`configkey::effect_for_affected`). An ignored config has no copy in that commit, so it is compared with the defaults, as an untracked one is. A command or a shared setting that an ignored config sets therefore counts as changed in every `--affected` run and every run of the stop hook: the projects it reaches are affected each time, and their kept passes are served when their files did not change. An ignored config that only sets time limits affects nothing.
- **Its bytes in the key.** For a unit whose scope contains the repo root, the bytes are read from disk when git does not list the file (`stepcache::list_files`), so they are in the key like those of a tracked config. It is the only ignored file in a key.
- **Its bytes under `--affected`.** No commit has a copy to compare the bytes with. Counting an ignored config as changed in every run is the safe side, but a bad trade: a root project's key covers the whole repo, so it would run for real in every `--affected` run of a repo that has one, whatever changed. So the bytes are compared with what the last verify run that passed saw. `.firescale/ignored-config.digest` holds their digest; it is written at the end of a verify run whose result is `ok` or `partial`, from the bytes read before any step ran. When the digest differs, or there is none, the units whose scope contains the repo root run, with the reason `firescale.config.json, which git ignores, changed since the last run that passed, and these steps can read every file of the repo, the config among them`. A run in which something failed writes nothing, so the next run runs them again.
- **Why that lets no change through.** The record changes only at the end of a run in which nothing failed. In such a run each of these units either ran with the new bytes (or was served under a key that holds them), or was left out because the record already held the same digest. With no record (a new clone, `.firescale` deleted) the units run once.
- **The base.** A step whose key holds the ignored config as a file is never "the same on the base": the base commit has no copy of it. For a step below the root, what the config's difference reaches is asked whether or not the changed files name the config (`StepCache::same_on_base`).

Not covered: a `firescale.config.ts` that git ignores. Its commands and shared settings are in the keys by value, but its bytes are not, and `--affected` does not compare it. `check --affected` also still takes "the config changed" from git's list (ADR 0056), so it does not see a change to an ignored config.

### A config this version cannot read

`resolve_config` refuses a key it does not know, at every level, so a working tree whose config has such a key runs no step at all. The base commit's config may still have one: a teammate on a newer firescale wrote it, or this checkout rolled firescale back. Then:

- an unknown key inside `verify`, or a value `verify` cannot parse, makes the base's config unreadable: every project is affected;
- an unknown top-level key is part of the base's other settings, which then differ from the working tree's: every project is affected. Such a key is listed under its name followed by ` (an unknown key)`, so it never shares a name with a setting this version knows: a top-level key spelled `"verify.ci"` cannot stand in for the real `verify.ci`.

Either way an unknown setting counts as "in, all".

### A `firescale.config.ts`

A TypeScript config is code. It can read the environment, the clock or other files, and firescale cannot run the base commit's copy without checking that commit out. So the whole-file rule stays for it:

- its bytes stay in every step's key, as a root file no project owns;
- a change to it (or to any other root file named `firescale.config.*` that is not the `.json`) affects every project.

The shared settings digest is also made from the value the `.ts` config resolved to, so a value it computes differently from one run to the next (from an environment variable, say) changes the keys too. `verify --dry-run` still refuses a `.ts` config (ADR 0032).

### The base run of blame-aware verify, and the base store

The base run executes the **working tree's plan and settings** in a worktree of the base commit (ADR 0037); the base's config file is only a file there.

- **Same inputs** (`StepCache::same_on_base`): a step's head result is its base result when no file its key holds differs. For a step whose scope does not contain the repo root, the config is no longer such a file. So the step counts as the same only if the config comparison above (against the blame base, the same merge base) says no setting of that step changed, whether or not the config is among the files changed since the base. If the comparison was not made (a `firescale.config.ts`), a config among those files means the step does not count as the same. This keeps what 0.5.0 did for every change that matters, and adds the shortcut only for the "out" settings. For a step whose scope contains the repo root the config is a file of the key, so any byte change of it reaches the step and the base run is made, as in 0.5.0.
- **The base store's key** (`StepCache::base_key`) is the step's key (with the shared settings line, since the base step runs under the working tree's settings), the base commit, `environment` (links or `baseInstall`, env files) and the base's files. The base's config blob is among those files only for a step whose scope contains the repo root; the commit id, which fixes it, is there for every step.
- **The `fixed` pairing** (`blame::fixed_key`) is made from the base key and the head key, so it follows both.

### The shared CI cache

A record of the shared cache vouches for "this key passed on the default branch" (ADR 0041). It uses the same key, so the question is the same: can two runs with one key give different results? The key now misses the "out" settings only, and only for a step whose scope does not contain the repo root. A pull request that changes a time limit reads the default branch's records for those steps, which is the point; the root's own steps and a root project run again, since the file changed. The workflow file stays in every key in CI (`CiRun::key_salt`), unchanged.

### `fscale check`

- **The rule-result cache** (`crates/core/src/cache.rs`) does not share this mechanism: it keys a rule on the files its `inputs` name, its options and its status. It is not touched.
- **`check --affected`** (`affected::narrow_report`): ADR 0056, bug 1, made every rule read a change of the firescale config, because a config change can turn any rule on. That is about findings, not steps, and it stays: it is not loosened here. The cost is small (a kept finding, never a 100-minute test run), and loosening it needs the same per-setting comparison for rules, which nobody asked for.

### Why a time limit is out

A limit (`verify.timeout`, `verify.idleTimeout`, a step's or a project's `timeout`, `verify.baseBudget`) can only end a step early. What a step that was ended early becomes, in `verify::run_step`:

- `timed out`, or `setup needed` when a short second run names the environment. Never `passed`, never `failed`.

What each store keeps:

- the local step cache and the shared cache: only `passed` (`cached_or_run`, `StepCache::remember`);
- the base store: only `passed` and `failed` (`blame::keep`); a base step stopped by its limit is `timed out`, or `over-budget` when the budget ended it;
- the `fixed` pairing: the same `keep`.

So no limit can put a result into a store that a different limit would not also have put there, had the step finished. A longer limit lets a step finish that timed out before; that step was never stored, so it runs. A shorter limit may time out a step that passed before; its kept pass is still true of the code, and is served. That is the one seen change: **after a limit is lowered, a step that passed under the old limit is still served from the cache** rather than run again to see whether it now times out. It holds for a step in a project below the root. A step whose scope contains the repo root runs again after any edit of the config, because the file is in its key.

The limits are not passed to the commands: `verify::environment` sets `NO_COLOR`, `FORCE_COLOR`, `PYTHONUNBUFFERED`, `CI` and, on the base, `FSCALE_BASE_RUN`, and nothing from the limits.

### The note about a changed config

ADR 0043's note (`firescale.config.json changed since the last run, and it is part of every step's cache key ...`) is now said only when the shared settings changed since the last run, since only then does every key change. `.firescale/step-cache-config.digest` holds the shared settings digest (and the bytes of a `.ts` config), not the file's digest.

### The list of inert files stopped at the first widening file

Found through the owner's second report (an untracked `image.png` at the root was not listed as a file that cannot affect a build). `graph::affected` returned as soon as one file widened the run to every project, so files sorted after it were never looked at: with an untracked `firescale.config.json`, `image.png` comes later in the list and was never named. The walk now goes on to the end and lists every inert file, whatever else changed. Which projects run is unchanged.

## Consequences

- A config that only sets time limits or budgets, tracked or not, runs no project in a folder below the root under `--affected` and in the stop hook, and changes none of their cache keys. The owner's six projects are all such projects.
- Writing a default out in full, or reformatting the config, changes nothing for those projects either.
- The repo root's own steps, a root project and every other unit whose scope contains the repo root run again after any change to the config's bytes, as in 0.5.0. Only they do: the change no longer runs every project.
- Turning a rule on, or adding a pack, still runs every step once. That is the price of "unsure, so kept".
- Passes kept by 0.5.0 are not read by 0.5.1 (format 2): the first run after the upgrade runs every step.
- A step of a project below the root that passed is served from the cache after a time limit is lowered.
- One test changed on purpose: `step-cache.test.ts` "says once when a change to the config means no kept pass applies" wrote `"failOnSkipped": false`, which is the default, and expected every step to run again. It now checks that this (and a time limit) runs nothing, then turns `verify.ci` off, which is a real change. The note's text changed with it.
- The note that lists inert files names them whatever else changed.

**Known limits**

- A command of a project in a folder below the root that reads `firescale.config.json` itself, by a path that leaves its folder (a test that asserts the file's text, or a step that runs `fscale verify --dry-run` on the repo and compares the output), is not run again when only an "out" setting or the file's layout changes. A step whose scope contains the repo root is run again. No rule of firescale can see that a test opens a file by its path; ADR 0034 accepts the same for a root `README.md`.
- The same holds for a tool that a step of a project below the root runs and that finds its settings file at the repo root, when those settings make it read `firescale.config.json`: cspell started in a project's folder with a root `cspell.json` whose `files` reach the root, say. The settings file is in that step's key (it is a root file); the firescale config it points at is not.
- A rule that reads every file (`core/no-secrets-in-source`) reads the config's text too. A step of a project below the root that runs `fscale check` inside is not run again for a secret typed into an "out" setting; verify's own `check` step runs fresh in every run and reports it.
- A `firescale.config.ts` that git ignores, and `check --affected` with an ignored config: see "A config that git ignores".
- After only `verify.baseInstall` changes, a failing step of a project below the root whose files are the same on the base is `pre-existing` with no base run (see "What was tried against it").
- A custom pack's files and the modules a `.ts` config imports are files of the repo, keyed by ADR 0036's rules like any other. Nothing changes for them.

## After the review

A review of the first version proved two holes. Both have a test that failed first.

**1. The config left the key of steps that read it as a file (high).** The first version took `firescale.config.json` out of every key and out of the graph's walk. But a step that runs at the repo root can read the file: `prettier --check .` does. With a root project whose lint fails on a config with no line end, an untracked `{"verify":{"test":{"timeout":"2h"}}}` broke the lint, and firescale did not see it: the full run served the kept pass, `--affected` ran nothing and said the change "runs no project", and the stop hook let the agent stop.

- Tests: `config-affects.test.ts`, "runs the root project again for an untracked config that its lint reads, and blocks the stop hook", "runs the repo root's own steps again for a white space change of a tracked config" and "runs the root project, and no project below it, for a change of the config's bytes only"; in Rust, `the_json_config_is_a_file_only_in_the_key_of_a_unit_that_holds_the_repo_root`, `the_json_config_is_a_file_in_the_key_of_a_project_at_the_repo_root`, `a_changed_config_is_the_same_on_the_base_only_for_steps_it_does_not_reach`, `a_settled_file_is_a_changed_file_of_the_root_project_only` and `the_units_that_can_read_the_config_as_a_file_are_marked`.
- Decision: the by-value rule applies only to a step whose scope does not contain the repo root ("Where the config is still a file"). Three places follow it: `stepcache::covers` (the key, the base store's key and `same_on_base`), `graph::affected_except` (the root project) and `configkey::mark_file_readers` (every other unit that holds the root).
- The owner's case still holds: its six projects are in folders below the root and nothing runs at the root, so `--affected` runs 0 of 6.
- Tests that pinned the old rule for a root step were changed: the Rust test `the_json_config_is_in_no_key_as_a_file_but_its_shared_settings_are` (now the first Rust test named above), the root-step half of `a_changed_config_is_the_same_on_the_base_only_for_steps_it_does_not_reach`, and "never keeps a step that a limit stopped, and serves a kept pass after the limit is lowered", whose slow test was a root command and is now a project's in a folder below the root. The same move was made in `blame.test.ts` ("counts a step as the same on the base after a config change that cannot reach it, and runs the base after one that can") and `shared-cache.test.ts` ("serves a record to a pull request that changes a time limit, and not to one that changes a setting every step shares"); each has a new test beside it for a step of the repo root's own. `step-cache.test.ts` "says once when a change to the config means no kept pass applies" runs root steps: they now run again after the default is written out, while the note is still said only for `verify.ci`.

**2. An unknown key could take a setting's name (low).** `configkey::shared_parts` put every top-level key of the other settings into one map with the resolved `verify` settings. A base commit's config with a top-level key spelled `"verify.ci"` overwrote the resolved value of the real `verify.ci`, so a change of the real one was not seen.

- Test: `an_unknown_key_named_like_a_setting_cannot_hide_that_setting`.
- Decision: a top-level key this version does not know is listed as `<key> (an unknown key)`. No setting's name ends that way. `packs` and `rules` keep their names. The reason of an affected run shows the new name: `... changed (future (an unknown key))`.
- The working tree's config cannot have an unknown key, so no key of a working tree changes with this.

## After the second review

A second review confirmed both fixes above for a tracked config and for a plainly untracked one, and proved a gap for a config that git ignores (untracked, and matched by `.gitignore`). Each part has a test that failed first.

**1. `--affected` and the stop hook missed the settings of an ignored config.** `configkey::effect_for_affected` compared the configs only when git listed `firescale.config.json` among the changed files, and git lists an ignored file nowhere. With two projects and an ignored config that gave `web` a failing test command, `verify --affected` said `in web: not affected` where a full run fails. `StepCache::same_on_base` had the same gate.

- Tests: in Rust `a_config_that_git_ignores_is_compared_though_no_list_names_it` and `a_config_change_that_no_list_names_still_reaches_the_base_comparison`; in `config-affects.test.ts`, under "when git ignores the config", the tests for a project's command, `verify.ci`, `verify.failOnSkipped`, a time limit and the stop hook.
- Decision: the comparison is always made. A config with no copy in the comparison commit is compared with the defaults.

**2. The bytes of an ignored config were in no key.** The step cache lists files with `git ls-files --exclude-standard`, so an ignored config was never offered to `stepcache::covers`. A root lint that fails on a config with no final line end kept its pass after the config was rewritten that way. Read from the code of the commit this branch started from: the same list was used there, so this was so before this ADR.

- Tests: in Rust `a_config_that_git_ignores_is_a_file_of_a_key_that_holds_the_repo_root` and `only_a_config_that_git_ignores_has_a_digest_and_a_record`; in `config-affects.test.ts`, the three root-lint tests under "when git ignores the config".
- Decision: see "A config that git ignores": the bytes are read from disk for the keys that hold them; under `--affected` they are compared with what the last run that passed saw; such a step is never the same on the base.

**3. A wrong note after a rename.** After `git mv firescale.config.json firescale.config.ts`, `--affected` ran every project and still said that the change "runs no project". The note is now said only when nothing runs every project. Test: "does not say that the change runs no project after a rename from .json to .ts".

The owner's case holds with the config ignored too: "runs no project for a git-ignored config that only sets two test timeouts" (six projects below the root, nothing at the root) runs 0 of 6.
